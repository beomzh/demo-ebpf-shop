# 촬영 런북 — 배송 조회 실패 사건

영상별로 **촬영 직전에 무엇을 실행하고, 화면에서 무엇을 보여주고, 어떻게 말하는지**를 정리한 문서입니다.
준비·배포는 [README](../README.md)를 먼저 보세요.

- Observ 화면에서는 네임스페이스 필터를 **`demo-shop`** 으로 둡니다. (`demo-infra` 의 부하 발생기·사내 DNS 는 데모 장치입니다)
- 트랜잭션 조회의 소스 토글은 **eBPF** 로 둡니다.

---

## 0. 촬영 전날 — 정상 상태 데이터 쌓기

```bash
./demo.sh deploy          # 배포 직후 = 정상 상태 (주·보조 DNS 기동, 방화벽: 배송 → 주 DNS·택배사만 허용)
./demo.sh status          # 주·보조 DNS 파드 Running, 배송 파드 DNS 조회·TCP 연결 성공, 배송 조회 200, 체크아웃 201
```

- 최소 몇 시간, 가능하면 하루 이상 그대로 둡니다. 데모 2·3에서 조회 기간을 넓혀 주 DNS 로 정상 조회되던 모습과 비교합니다.
- `./demo.sh traffic` 으로 `201`(주문 생성)과 `200`(배송 조회)이 계속 찍히는지 확인합니다.

## 1. 사건 발생 — 촬영 시작 15~30분 전

```bash
./demo.sh incident        # 주 DNS 파드(ns1-corp-dns-0) 삭제 → 보조 DNS 로 넘어가지만 배송 서비스는 방화벽에 막힘
./demo.sh status          # 주 DNS 파드 없음, 배송 파드 DNS 조회 실패, 배송 조회 502, 체크아웃은 201
```

- SLO 경고와 T-Map 의 실패 영역이 보일 만큼 데이터가 쌓이도록 **촬영 전에 충분히** 둡니다.
- `./demo.sh traffic` 에서 배송 조회가 `502 2.0~4.0s` 로, 체크아웃은 `201` 로 찍히면 정상적으로 장애 상태입니다.

## 영상 ① 발견 (10분) — 데모 1

| 순서 | 화면 | 보여줄 것 | 말할 것 |
| --- | --- | --- | --- |
| 1 | (도입) | "배송 조회가 전부 실패한다"는 문의. 결제 등 다른 기능은 정상 | 배송 서비스는 모니터링이 없는 Python 서비스. 코드는 바뀐 게 없다 |
| 2 | 서비스 목록 | 게이트웨이·회원·상품·재고·주문·결제·알림·배송 여덟 서비스가 언어 아이콘(C#·Java·Go·Ruby·Node.js·PHP·Python)과 함께 나타나 있음 | 아무도 계측하지 않았는데 일곱 가지 언어가 이미 목록에 있다 |
| 3 | 토폴로지 맵 | 배송 서비스 노드의 경고. 배송 → 외부 택배사 연결선에 **최근 트래픽이 없음** | 배송 서비스가 택배사로 나가지를 못하고 있다 |
| 4 | 배송 서비스 상세 → SLO 탭 | 주문 서비스에서 들어온 요청이 2~4초 뒤 전부 오류로 끝남 (게이트웨이 → 주문 → 배송 경로) | 배송 조회가 몇 초 뒤 전부 실패한다 |

## 영상 ② 원인 (12분) — 데모 2, 3

| 순서 | 화면 | 보여줄 것 | 말할 것 |
| --- | --- | --- | --- |
| 1 | APM 대시보드 → T-Map | 실패 영역을 드래그 → **트랜잭션 조회** 창에서 배송 서비스 요청이 전부 2~4초 + 5xx | 실패는 전부 배송 서비스 |
| 2 | 배송 서비스 상세 → 네트워크 탭 | 택배사 IP 로 가는 TCP 연결이 **실패가 아니라 아예 없음** | 연결을 시도조차 못 한다 → 그 앞 단계, 이름 조회를 의심 |
| 3 | 배송 서비스 상세 → 도메인네임(DNS) 탭 | 택배사 도메인(`api.courier.example`) 조회가 **응답 없이 실패**(타임아웃·지연) | 택배사 도메인을 찾지 못하고 있다 |
| 4 | 결제 서비스 상세 → DNS 탭 (비교) | 같은 시각 PG 도메인 조회는 정상 | 사내 DNS 가 다 죽은 건 아니다. 배송 서비스에서 가는 길만 막혔다 |
| 5 | 터미널: `oc -n demo-infra get pods` | `ns1-corp-dns-0` 없음, `ns2-corp-dns-0` 만 Running | 주 DNS 가 죽었다. 보조 DNS 는 살아 있는데 배송만 못 쓴다 |
| 6 | 터미널: `./demo.sh firewall` | 배송 서비스 방화벽에 **주 DNS 만** 있고 보조 DNS 는 없음 | 방화벽 신청 때 보조 DNS 를 빠뜨렸다. 평소엔 주 DNS 가 답해서 아무도 몰랐다 |

`./demo.sh firewall` 출력 예:

```
RULE                         DESCRIPTION
fw-allow-corp-dns-primary    사내 주 DNS (ns1-corp-dns) 53 허용
fw-allow-courier-10-0-0-61   택배사 API (api.courier.example) 10.0.0.61:443 허용
fw-delivery-default          배송 서비스 egress 기본 규칙: 허용 목록 외 모두 차단
```

(선택) 터미널에서 `./demo.sh corpdns logs` 를 띄워 두면, 보조 DNS 에는 결제 파드의 질의만 찍히고 배송 파드의 질의는 오지 않는 것이 보입니다.

## 영상 ③ 해결과 표준화 (10분) — 데모 4

```bash
./demo.sh fix             # 방화벽에 보조 DNS 허용 추가
./demo.sh firewall        # fw-allow-corp-dns-secondary 가 추가된 것 확인
./demo.sh status          # 배송 파드 DNS 조회 성공(보조 DNS), 배송 조회 HTTP 200 — 주 DNS 는 아직 없음
```

| 순서 | 화면 | 보여줄 것 | 말할 것 |
| --- | --- | --- | --- |
| 1 | 배송 서비스 상세 → DNS 탭 | 방화벽 허용 이후 택배사 도메인 조회 성공 | 주 DNS 가 아직 복구 중인데도 보조 DNS 로 회복했다 |
| 2 | 배송 서비스 상세 → 네트워크 탭 | 택배사 IP 로 가는 TCP 연결이 다시 생김 | 이름을 찾으니 연결도 된다 |
| 3 | APM 대시보드 → T-Map | 실패 영역이 사라짐 | 사용자 요청도 정상으로 돌아왔다 |
| 4 | 서비스 목록 (또는 커스텀 대시보드 RED 템플릿) | C#·Java·Go·Ruby·Node.js·PHP·Python 여덟 서비스를 요청 수·지연·오류로 나란히 비교 | 언어·팀·도구가 달라도 같은 기준으로 본다 |
| 5 | 한계 장표 | 서비스 간 요청 1건 추적, 앱 내부 외부 호출 실패 원인 → OpenTelemetry 와 함께 (EP05) | eBPF 가 못 보는 부분은 다음 편에서 |

- `./demo.sh fix` 직후 바로 녹화하지 말고 1~2분 기다려 차트에 변화가 반영된 뒤 보여줍니다.
- `fix` 뒤에도 주 DNS 가 없는 동안은 조회마다 주 DNS 타임아웃만큼(최대 2초) 느릴 수 있습니다 — "주 DNS 도 복구해야 원래 속도" 로 마무리.

# 정상 데이터가 몇 분 쌓인 뒤

## 시나리오 2 — DNS 이름 변경 → 없는 이름 조회 (결제 서비스)

시나리오 1(배송 조회 실패 사건)과 별개로 촬영합니다. 로그 예시는 [README 6-2](../README.md#6-2-시나리오-2--dns-이름-변경-없는-이름-조회).
장애는 **결제 서비스(Node.js)** 에서만 납니다 — 외부 PG 를 부르는 유일한 서비스입니다.

| 순서 | 명령 | 화면 | 보여줄 것 | 말할 것 |
| --- | --- | --- | --- | --- |
| 0 | `./demo.sh pg-status` | | 주·보조 DNS 모두 PG IP, 체크아웃 201 | 결제 서비스는 사내 DNS 로 PG 도메인을 찾아 승인을 요청한다 |
| 1 | `./demo.sh pg-missing` | 결제 서비스 상세 → DNS 탭, 체크아웃 오류율 | 새 PG 도메인(`api-new…`) 조회의 **NXDOMAIN** 증가 | PG사 도메인 이전 후 결제가 전부 실패 — 코드가 아니라 사내 DNS 등록 누락 |
| 2 | (터미널) `oc -n demo-shop logs deploy/payment-service --since=1m \| jq -r 'select(.msg=="upstream call failed") \| .error' \| tail -1` | 결제 서비스 로그 | `Error: getaddrinfo ENOTFOUND api-new.pg.example` | 앱은 "이름을 찾지 못했다"는 예외만 남긴다 — 원인은 eBPF DNS 탭이 먼저 보여줬다 |
| 3 | `./demo.sh pg-register` | DNS 탭, 체크아웃 | NXDOMAIN 멈춤, 체크아웃 201 | 사내 DNS 에 한 줄 등록하자 **앱 재시작 없이** 회복 |
| 4 | `./demo.sh pg-reset` | | 원래 상태 | 다음 테이크 준비 |

- PG 호출(HTTPS)의 내용은 Node.js 라 eBPF 로 볼 수 없습니다. 대본에서 "PG 호출 오류율" 대신 **DNS 탭의 NXDOMAIN** 으로 말합니다.

## 촬영 전 확인 (실제 화면에서)

- [ ] 배송 서비스 DNS 탭에 **응답 없는 DNS 조회(타임아웃)** 가 실패·지연으로 보이는가 — 보이는 방식(오류 수, 지연, 응답 코드 없음)을 확인해 대본 표현을 맞춘다
- [ ] 배송 서비스 네트워크 탭에서 incident 이후 택배사 IP 로 가는 TCP 연결이 사라지는 것이 보이는가
- [ ] 토폴로지 맵: 트래픽이 끊긴 배송 → 택배사 연결선이 어떻게 표시되는가 (사라짐 / 흐리게 / 그대로)
- [ ] 배송 서비스 노드 경고: 주문 → 배송 요청의 오류율이 SLO 임계치(기본 가용성 99%)를 넘는가
  - 장애 중 배송 조회는 100% 실패하므로 넘어야 정상. 안 보이면 SLO 평가 주기만큼 더 기다린다
- [ ] 드래그로 열리는 창 이름이 "트랜잭션 조회"인가 ("요청 뷰어"는 다른 위젯 — 대본에서 섞어 쓰지 않음)
- [ ] 스팬 워터폴은 EP05 범위 — 이 편에서는 트랜잭션 조회 목록까지만
- [ ] Cassandra·RabbitMQ 는 이 편에서 언급하지 않음 (이 데모에는 없음)
- [ ] 서비스 목록의 언어 아이콘: 게이트웨이 C#(.NET) / 회원·주문 Java / 상품 Go / 재고 Ruby / 결제 Node.js / 알림 PHP / 배송 Python
  - Observ 가 C#·Ruby·PHP 를 언어로 표시하는지 실제 화면에서 확인 (표시되지 않으면 대본에서 해당 언어 언급을 빼거나 서비스 목록 장면에서 설명을 조정)
- [ ] 토폴로지: 배송 장애 시 게이트웨이·주문 노드에도 오류가 번져 보일 수 있음 (하위 5xx 가 위로 전달됨). 원인은 배송 서비스의 DNS 조회임을 대본에서 짚기
- [ ] 평소(정상) DNS 탭: `api.courier.example` 조회가 보이고 NXDOMAIN·ServFail 이 0
